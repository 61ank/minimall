---

## 1. 项目概述与目标

构建一个可运行的**精简 B2C 电商后端 REST API**，覆盖核心购物闭环：

> 商品浏览/搜索 → 加入购物车 → 下单 → 支付(模拟) → 订单履约(发货/完成)，以及库存防超卖与取消回补。

**目标：**
- 验证并串联多模块、事务一致性、并发控制、缓存、搜索、自动化测试等工程能力。
- 作为后续阶段（架构 / 数据库 / 编码 / 测试 / Docker / CI/CD / AI）的迭代基座。

---

## 2. 角色与用户

| 角色 | 说明 | 核心诉求 |
|---|---|---|
| 游客 | 未登录用户 | 浏览、搜索、查看商品详情 |
| 买家 | 注册用户 | 购物车、下单、支付(模拟)、查看订单、评价 |
| 管理员 | 平台运营 | 商品/分类/库存管理、订单履约（发货/完成）、数据查看 |

> 鉴权方式（JWT 等）属架构阶段决策，本阶段只声明"需要身份认证与角色区分"。

---

## 3. 范围划分

- **MVP（核心闭环，必做）**：用户、商品(含分类)、购物车、订单、库存、支付(模拟)、搜索(基础)、Redis 缓存。
- **后期 v2（可选增强）**：评价 + AI 情感分析、优惠券、AI 推荐。
- **基础设施（贯穿）**：统一错误处理、日志、健康检查、配置管理、自动化测试、CI、数据库迁移。

## 4. 功能需求

### 4.1 用户模块
**用户故事：**
- 作为买家，我想要注册/登录，以便身份被识别并管理我的购物与订单。
- 作为用户，我想要维护个人资料与收货地址，以便下单时选择。

**功能点：**
- 注册（唯一性校验：用户名/邮箱）、登录、登出（token 失效策略）
- 获取/更新个人资料
- 收货地址增删改查（可设默认地址）

**验收点：** 注册→登录→携带 token 访问受保护接口全链路可用；非法/过期 token 返回 401。

### 4.2 商品模块
**用户故事：**
- 作为游客，我想要按分类/关键词/价格筛选并排序浏览商品，以便快速找到目标商品。
- 作为管理员，我想要维护商品与分类，以便平台有可售商品。

**功能点：**
- 分类树管理（增删改查，管理员）
- 商品 SPU/SKU 维护（增删改查、上/下架，管理员）
- 商品列表：分页、筛选（分类/价格区间/上下架状态）、排序（价格/销量/上架时间）
- 商品详情：基本信息、SKU 与库存、评分（后期评价接入后）

**验收点：** 列表分页与筛选正确；SKU 级库存可见；下架商品不出现在游客列表。

### 4.3 购物车模块
**用户故事：**
- 作为买家，我想要把商品加入购物车并调整数量，以便集中结算。

**功能点：**
- 加入购物车（校验 SKU 存在且在售；数量上限）
- 修改数量、移除单项、清空
- 查看购物车（含单价快照、小计）
- 加购时校验库存，超出时提示

**验收点：** 购物车操作只对自己可见；加入已下架/超库存商品被拒绝并给出明确错误。

### 4.4 订单模块
**用户故事：**
- 作为买家，我想要从购物车下单并支付(模拟)，以便完成购买。
- 作为管理员，我想要对订单发货/标记完成，以便履约。

**功能点：**
- 从购物车创建订单：生成订单（主表+明细，含单价快照）、扣减库存（与库存模块联动，事务性）
- **幂等**：重复提交同一购物车不产生重复订单（防抖）
- 取消订单：仅待支付可取消，取消后恢复库存
- 支付(模拟) → 订单变更为已支付
- 管理员发货 → 已发货；买家确认 → 已完成（或管理员标记完成）
- 订单列表（按状态/时间筛选）、详情、订单号唯一
- **订单状态机**：
  ```
  待支付(CREATED) → 已支付(PAID) → 已发货(SHIPPED) → 已完成(COMPLETED)
       └─────────→ 已取消(CANCELED)
  ```
  非法状态迁移必须被拒绝。
- （后期）超时未支付自动取消——需定时任务，排期到基础设施完善后

**验收点：** 下单→支付→发货→完成全链路；取消订单库存回补；非法状态迁移返回错误。

### 4.5 库存模块
**用户故事：**
- 作为管理员，我想要维护每个 SKU 的库存，以便真实反映可售数量。
- 作为平台，我想要在并发下单时不超卖，以便库存数据准确。

**功能点：**
- 库存维护（设库存、加库存、查看，管理员）
- 下单时**原子扣减**（`库存充足才扣`，防止超卖；如 SQL `UPDATE ... WHERE stock >= n` 或 Redis 预扣）
- 取消/退款时回补库存

**验收点：** 并发 100 个请求抢购同一 SKU（库存 10），成交数 ≤ 10 且无负数库存。

### 4.6 支付模块（模拟）
**用户故事：**
- 作为买家，我想要为待支付订单完成支付，以便订单进入履约。

**功能点：**
- 发起支付：生成支付单，对接**模拟支付通道**（本地 mock，不接真实渠道）
- 支付回调（模拟）：成功后回调系统，订单置为已支付
- 仅"待支付"订单可支付；支付成功幂等（重复回调不重复处理）

**验收点：** 支付成功后订单状态正确且不可重复支付。

### 4.7 搜索模块（基础 → 后期 ES）
**用户故事：**
- 作为游客，我想要按关键词搜商品，以便快速找到目标。

**功能点：**
- MVP：基于 SQL 的关键词模糊搜索（`LIKE`/全文索引）兜底
- 后期：接入 Elasticsearch，实现全文检索、高亮、相关性排序
- 商品上/下架与信息变更时同步索引（后期）

**验收点：** 关键词可命中标题/描述；搜索与筛选、分页可组合。

### 4.8 缓存与基础设施需求（Redis）
**功能点：**
- 热商品/商品详情缓存（缓存穿透/击穿/雪崩的基础防护）
- 购物车（可选：Redis 或 MySQL，架构阶段定）
- 库存预扣/防超卖辅助（架构阶段定策略）
- 全局：统一错误响应、请求日志、`/health` 健康检查、配置走环境变量

**验收点：** 热接口命中缓存后响应显著下降；缓存与库数据最终一致。

### 4.9 AI 能力（后期 v2）
- 评价情感分析、简单推荐（基于销量的"猜你喜欢"起步，再考虑模型）。

## 5. 非功能需求

### 5.1 性能
- 读接口 P95 响应 ≤ 300ms；命中缓存的热点接口 ≤ 50ms。
- 支持约 100 并发用户；抢购场景库存不超卖。
- 数据库与缓存连接池合理配置，避免连接泄漏。

### 5.2 安全
- 密码哈希存储（bcrypt 等，禁止明文）；登录失败限流。
- 身份认证 + 角色鉴权（管理员接口必须鉴权）；越权访问被拒绝。
- 输入校验（pydantic）、防 SQL 注入（ORM）、CORS 策略、敏感配置走环境变量不入库不入 git。

### 5.3 可用性
- 统一异常处理与结构化错误码；外部依赖（DB/Redis）故障时给出可理解的错误而非 500 崩溃。
- 健康检查接口；启动配置校验失败时快速失败。

### 5.4 可维护性
- 分层清晰：router → service → repository（或等价分层），职责单一。
- 类型标注（mypy/pyright 友好）、lint（ruff）、统一格式化。
- 数据库结构变更走迁移（Alembic）；配置集中管理（pydantic-settings）。
- 代码可被测试：业务逻辑与框架解耦。

### 5.5 测试
- 单元测试 + 集成测试 + API 测试；核心业务（订单/库存/鉴权）覆盖率目标 ≥ 80%。
- 测试数据库隔离（独立库/事务回滚）；关键并发用例覆盖（库存防超卖）。
- CI 中自动执行 lint + 类型检查 + 测试。

## 6. 验收标准（可验证）

1. 注册 → 登录 → 携带 token 访问受保护接口全链路可用。
2. 商品 CRUD、列表筛选/分页/排序可用；下架商品不出现在游客列表。
3. 购物车增删改查可用，仅本人可见。
4. 下单 → 支付(模拟) → 发货 → 完成全链路跑通。
5. **并发 100 抢购同一 SKU（库存 10），成交 ≤ 10，库存不为负。**
6. 取消待支付订单，库存正确回补。
7. 关键词搜索可命中商品，且可与筛选/分页组合。
8. 核心接口均有自动化测试，本地与 CI 全部通过。
9. Docker 化后一键启动即可运行完整系统（后期）。
10. 所有配置与密钥不入库；`/health` 可用。
