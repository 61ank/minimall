- **补充（代码 Review 发现并修复）**：日志此前"只配置未使用"——兜底异常处理器注释写"细节依赖日志"却从不打日志，未捕获异常被吞掉；已补 `logger.exception`（含堆栈）+ 应用启动日志，验证日志真正生效

**Debug：POST 中文 body 报 400（现象 → 定位 → 修复）**
- **现象**：`curl -d '{"nickname":"测试用户"}'` 报 `400 There was an error parsing the body`。
- **定位**：Git Bash 调用原生 Windows 程序（curl.exe）时把命令行参数转成 ANSI 代码页（GBK），中文被转成 GBK 字节、破坏 UTF-8 JSON。
- **修复**：JSON 写入 UTF-8 文件后 `curl --data-binary @file`（走文件字节，不经命令行参数编码转换）；验证通过。
- **关联**：与 mysql 乱码同根（Windows GBK 代码页），属一类环境坑。

**对应意义（练到的 Claude Code 能力）：**
- **让 Claude 先立"纵向切片"样板、后续模块照模式扩展** → 驱动指令："给一个模块的 schemas→service→router 样板，让后续模块照模式实现"
- **全链路真实验证，含失败路径** → 驱动指令："每个接口不只测成功路径，还要验证 401/404/409/400 等失败路径，用真实请求实测"
- **Review 发现"配置了没用上"（logging）** → 驱动指令："让 Claude 自查基础设施是否在真实路径上被调用，而不只是配置了"
- 背景：JWT、bcrypt、错误码格式（AppError {code,message}）属框架/工程知识，降为背景；curl 中文编码坑并入"做了什么"

## 轮次 13 · 阶段八：购物车模块

**日期：** 2026-08-14

**做了什么：**
- 按纵向切片样板实现购物车：schemas（CartItemOut/AddCart/UpdateCart）→ service（加购/累加/改量/移除/清空/列表 + 库存校验）→ router（/cart，全部需登录）
- 边界：数量 1~99（超上限 400）、库存不足 409、SKU 停售/商品下架 404、未登录 401
- curl 全链路验证：加购→累加(5)→改量(10)→移除→清空 + 全部失败路径 + /health 无回归

**Debug：/cart 全 404（现象 → 定位 → 修复）**
- **现象**：购物车接口全部 `404 Not Found`，但 /health、登录正常。
- **定位**：先查代码（main.py 已含 cart 路由）→ 再看运行环境：`netstat` 发现 8000 端口被**之前测试残留的旧 uvicorn（PID 22652）占用**，新服务日志报 `[Errno 10048] 端口只允许使用一次` 绑定失败——curl 打到的是没有 cart 路由的旧服务。
- **修复**：`taskkill //F //PID 22652` 杀残留进程，重跑全部通过。
- **教训**：遇到"新路由 404"先怀疑环境（端口占用/残留进程），再看代码；新服务启动日志明确报绑定失败。

**对应意义（练到的 Claude Code 能力）：**
- **让 Claude 复用样板快速加新模块** → 驱动指令："新增模块沿用既有样板（依赖注入 current_user、统一错误码），不要另起炉灶"
- **先查环境再怀疑代码** → 驱动指令："路由 404 先看新服务日志、查端口占用（netstat）与残留进程（tasklist），再查代码"
- 背景：用户专属资源、库存校验、错误码映射（400/409/404/401）属业务/工程知识，降为背景；bash 引号陷阱属环境操作细节，并入"做了什么"

**日期：** 2026-08-14

**做了什么：**

- 库存防超卖：`UPDATE inventory SET available=available-:n WHERE sku_id=:s AND available>=:n`，影响行数=1 才成功
- 支付服务：发起 mock 支付单、回调（幂等：已 SUCCESS 直接返回，不重复处理）
- routers：/orders（下单/列表/详情/取消/发货/完成）、/payments（发起/回调）
- 全链路验证通过；**并发 20 抢库存 10 → 恰好 10 成功、10 个 INSUFFICIENT_STOCK、库存 0 不为负**

**Debug：发货/完成/取消全 500（现象 → 定位 → 修复）**
- **现象**：ship/complete/cancel 全部返回 500，但下单、支付、回调正常。
- **定位**：上一轮补的 `logger.exception` 派上用场——日志显示 `NameError: name '_transition' is not defined. Did you mean: 'transition'?`。函数定义名为 `transition`，三处调用写成了 `_transition`（先定私有名、后因 payments 复用改公开名，忘记同步调用处）。
- **修复**：三处调用改回 `transition`，重跑全链路通过。
- **教训**：重命名函数时若被多处调用，用全局搜索确认全部调用点同步，否则运行到才报错（Python 无编译期检查）。

**对应意义（练到的 Claude Code 能力）：**
- **让 Claude 实现复杂事务逻辑并要求自查** → 驱动指令："核心交易链路交给 Claude 实现，要求事务内完成全部写操作、任一步失败整体回滚"

- **并发正确性用真实并发脚本验证** → 驱动指令："防超卖等并发逻辑，要求 Claude 写并发脚本实测（N 并发抢库存），断言不超卖、不为负，不假设正确"

### 1. 测试体系（pytest 三层 + 覆盖率）——最优先，所有后续阶段的地基

**能力点：** 让 Claude 编写并运行测试、用覆盖率报告定位薄弱、改代码后跑回归验证——这是"让 Claude 验证自己的修改"的核心手段，也是重构/CI/Docker 的前置。

**驱动指令：**
> "为 auth/用户/商品/购物车/订单模块补三层 pytest：单元=service 纯逻辑（状态机迁移、金额计算）、集成=service+真实 MySQL 测试库、API=FastAPI TestClient 全链路（注册→下单→支付）。用 `app.dependency_overrides[get_db]` 把测试请求指向独立测试库。跑 `pytest --cov=app --cov-report=term-missing`，根据覆盖率报告补核心业务（订单/库存/鉴权）到 ≥80%。"

**教学要点：**
- **三层各自测什么**：单元测"一个函数给定输入的正确输出"（无 DB/网络）；集成测"service+真实库"的协作（事务、约束）；API 测"HTTP 全链路"（参数校验、鉴权、错误码）。
- **测试隔离**：测试库用独立 schema（如 `minimall_test`），测试前后清库；用 `conftest.py` 的 fixture（`scope="session"` 建引擎、`scope="function"` 开事务回滚）。
- **依赖覆盖**：`app.dependency_overrides[get_db] = test_get_db` 是 FastAPI 测试的精髓——不依赖真实生产依赖。
- **覆盖率是手段不是目的**：先保核心业务 ≥80%，不追 100% 的边缘分支。
- **回归测试**：任何修改后 `pytest` 全量通过才叫"没破坏"——这是后续重构的护身符。
- **Mock**：外部依赖（LLM、真实支付）用 Mock 替换，让测试快、确定、可离线。

**本项目练习：** 为 `services/orders.py` 的状态机 `transition()` 写单元测试（含全部非法迁移分支）；为下单写 API 测试覆盖"库存不足 409 / 空购物车 400 / 未登录 401"。

### 2. Code Review

**能力点：** 让 Claude 按维度系统审查代码，找到 Bug、设计、安全、性能、可维护性问题——这是"写完不等于完"的分水岭。

**驱动指令：**
> "对当前全部代码做 Code Review，按 6 个维度：①正确性（逻辑/边界/并发）②安全（注入/越权/密钥/输入校验）③性能（N+1/无索引/重复查询）④可维护性（分层职责/重复/魔法数字/命名）⑤测试充分性 ⑥异常处理。每个问题给出：文件:行号、严重度（高/中/低）、修复建议。只报真问题，不夸。可先用 `git diff` 对最近改动做变更级 Review。"

**教学要点：**
- **Review 的 prompt 要"指定维度 + 要求定位到行 + 区分严重度"**——泛泛问"帮我看看代码"会得到泛泛回答。
- **越权是电商头号安全点**：所有操作是否都带了 `current_user`？本项目购物车/订单已示范，Review 时要盯住有没有漏。
- **性能重点**：N+1（循环里查库）、缺索引的热点查询、大列表无分页。
- **边界**：空购物车、超库存、重复回调、非法状态迁移——需求文档的验收标准就是 Review 的检查清单。
- **分级**：高危（数据损坏/越权/注入）> 中危（性能/可维护）> 低危（风格）。

**本项目练习：** 让 Claude Review `services/products.py`（价格子查询、排序白名单）和 `services/orders.py`（事务、状态机），看能否找出 2 个以上真实问题。

### 3. 重构 Refactoring

**能力点：** 让 Claude 在测试保障下改结构、不改行为——"修改已有代码"能力的最高形态。

**驱动指令：**
> "重构前先保证 pytest 全绿。执行流程：现状分析 → 重构目标 → 方案 → 小步执行（每步跑测试）→ 全量测试对比重构前后行为一致 → 汇报改动。候选：把 service 里的数据访问抽成 repository 层；修复商品列表的 N+1 查询；拆分 orders.py 里的大函数。"

**教学要点：**
- **重构铁律：没有测试别重构**（#1 为什么最优先）。行为是否一致的唯一判据是测试。
- **小步重构**：一次只改一件事，每步跑测试，失败能定位到那一步。
- **可重构的信号**：重复代码、大函数（>50 行）、职责混杂、魔法数字/字符串、直接绕过分层。
- **重构≠重写**：重写是丢弃实现；重构是逐步变换保持行为。让 Claude 明确区分。
- **本项目例子**：`orders.py` 已 194 行，可拆；商品列表用标量子查询可改为更清晰的 repository 封装。

**本项目练习：** 抽 repository 层（`get_sku_with_stock` 等），重构前后跑同一批测试断言结果一致。

### 4. Redis 缓存接入

**能力点：** 让 Claude 接入外部组件并**改造已有代码**（Cache-Aside），处理缓存一致性。

**驱动指令：**
> "启动本地 Redis（redis-server），配置 REDIS_URL。对商品详情 GET /products/{id} 与列表做 Cache-Aside：读先查 Redis，未命中查 MySQL 回填；商品上/下架、改价、改库存时删除对应缓存 key。key 规范：`product:detail:{id}`、`product:list:{参数hash}`，TTL 60s。实测：首次请求走库、二次命中（响应时间下降）、改商品后缓存失效拿到新数据。浏览计数用 Redis INCR 提供 GET /products/{id}/views。"

**教学要点：**
- **Cache-Aside 是默认选择**：读未命中回填 + 写时删缓存。写时"删缓存"而非"更新缓存"（避免并发写不一致）。
- **key 设计**：含业务+ID+参数；有 TTL 防无限增长。
- **三大经典坑**：穿透（查不存在的东西，可加空值缓存）、击穿（热点 key 过期，加互斥锁重建）、雪崩（大量 key 同时过期，TTL 加随机抖动）。
- **一致性**：缓存是加速不是事实源，最终一致可接受；本项目的强一致场景（库存）绝不走缓存。
- **验证是重点**：命中/失效都要实测，别只看"代码写了缓存"。

**本项目练习：** 商品详情缓存 + 改价后失效的完整验证（对比响应时间或加日志）。

### 5. Elasticsearch 搜索

**能力点：** 让 Claude 安装/接入 ES、设计索引、做数据同步、把 SQL LIKE 替换为 ES 检索。

**驱动指令：**
> "安装并启动 Elasticsearch，设计 products 索引（title/description 分词、category/price 过滤字段），实现商品变更（上/下架、改名、改价）后的索引同步，把 /products 的 q 参数从 SQL LIKE 改为 ES 检索，保留筛选/分页/排序组合，返回高亮片段。用种子数据对比 SQL 与 ES 的搜索命中与相关性。"

**教学要点：**
- **ES 解决什么**：相关性排序、分词（中文需 ik 分词器）、模糊命中——SQL LIKE 做不到。
- **索引与库是两套**：ES 是搜索副本，MySQL 是事实源；**同步**是关键（新增/改/删都要同步，本项目可用同步写或异步队列）。
- **Mapping 设计**：哪些字段分词、哪些 keyword、哪些数值范围。
- **检索与筛选**：bool query（must 关键词 + filter 分类/价格/状态）。
- **易错点**：索引与库不一致（同步漏了）、ES 宕机降级（回退 SQL）。
- **本机装 ES 需要 JDK 与内存配置**，正好练"让 Claude 处理环境安装"。

**本项目练习：** 用"手机"等关键词对比 SQL 与 ES 的命中差异。

### 6. 定时任务 / 后台任务

**能力点：** 让 Claude 引入调度机制处理后台工作（订单超时未支付自动取消）。

**驱动指令：**
> "实现订单超时未支付自动取消：定期扫描 PENDING 超 15 分钟的订单→取消→回补库存。用 APScheduler（轻量，进程内）或 RabbitMQ 延迟消息（重量级，需装）二选一并给出理由。任务要幂等（重复执行无副作用）、与主流程解耦、有日志与失败重试。"

**教学要点：**
- **取舍**：APScheduler 简单、单机够用；Celery/RabbitMQ 适合多实例、重任务——本项目规模 APScheduler 足够。
- **幂等**：后台任务可能重复跑，取消已取消的订单要安全（本项目状态机天然防重复）。
- **边界**：扫描间隔与订单金额一致性、任务启动时补扫。
- **生产思维**：任务日志、失败重试、监控——这本身是"让 Claude 考虑非功能需求"的训练。

**本项目练习：** 造一个 PENDING 超时订单，跑任务验证被取消且库存回补。

### 7. Skills（项目级）——Claude Code 独有，最值得学

**能力点：** 理解 Skill 是什么、何时建、如何设计、如何调用；把高频流程固化为可复用 Skill。

**驱动指令：**
> "把『新增一个业务模块』固化为项目级 Skill：读取现有样板（如 cart），编写 .claude/skills/add-module/SKILL.md（frontmatter 声明 name/description，正文写步骤：schemas→service→router→main 接入→curl 验证→补测试），说明触发场景。然后示范调用它新增一个模块。"

**教学要点：**
- **Skill vs CLAUDE.md**：CLAUDE.md 是"项目上下文"（每次会话加载的信息）；Skill 是"可执行流程"（按需触发的固定操作步骤）。
- **何时该建**：高频、流程固定、可复用（"新增模块"、"发版前检查"、"写测试"）；低频一次性任务不要建。
- **Skill 结构**：`.claude/skills/{name}/SKILL.md`，frontmatter 有 `name`/`description`（description 用于触发匹配）。
- **怎么调用**：`/skill-name`，或描述里命中触发。
- **价值**：把团队最佳实践固化，任何人/会话一句触发执行整套流程。

**本项目练习：** 用提炼出的 Skill 新增一个"收藏夹"模块，检验 Skill 流程是否够通用。

### 10. AI / LLM 能力

### 11. Docker 化

**驱动指令：**

### 12. CI/CD（GitHub Actions）

**能力点：** 让 Claude 建 CI 工作流、推送自动触发、CI 失败时按日志定位修复。

**驱动指令：**
> "创建 .github/workflows/ci.yml：push/PR 触发，jobs：setup-python 3.14 → 装依赖 → ruff lint → pytest 全量（含覆盖率）→ 上传覆盖率报告。推送触发后观察 CI 运行；若失败，读 CI 日志定位并修复到绿。"

**教学要点：**

- **失败修复闭环**：CI 红→读日志→定位→修→重推→绿，是"让 Claude 处理远程环境问题"的训练。
- **与本地差异**：本地 .env 不在 CI，密钥走 GitHub Secrets。

**本项目练习：** 推送一个故意失败（如断掉的测试）观察 CI 报错，再修复到绿。

## 轮次 17 · 多 Agent 流水线：触发方式与模型切换（承接轮次 16 复盘）

**日期：** 2026-08-14

**做了什么：**
- 记录"贵模型设计 → 评委 → 便宜实施"流水线的**触发方式**与**模型切换机制**（承接轮次 16 的演示）

**结论：**

### 1. 触发方式（三档驱动指令，你只需给一句"模式 + 任务"）
- 简单："用贵模型设计 + 便宜模型实施的模式，做 X"
- 明确："用 Opus 设计规格 → 另一个 Opus 评审 → Haiku 按规格实施 → 你验证，做 X"
- 脚本化（Workflow）："写一个 workflow：设计 → 评委 → 实施 → 验证，各阶段指定模型"

### 2. 模型切换机制（关键：你全程无需手动切）
- 主会话模型 = 你用 `/model` 设的（当前 opus），是"总指挥"，全程不变。
- **模型切换发生在主 agent 调用子代理时**，逐代理指定 model（opus/sonnet/haiku）。
- 你全程不碰任何设置；流水线内部程序化分配模型。

### 3. 手动切 vs 交给总指挥编排
| 方式 | 怎么做 | 优缺点 |
|---|---|---|
| 交给总指挥编排（推荐） | 一句指令，内部多 agent | 省事；规格衔接由 agent 保证（即轮次 16 演示） |
| 自己手动切 `/model` | 自己设计 → `/model haiku` 粘贴规格 → 实施 → `/model opus` 验证 | 可行但繁琐：规格要自己写到 airtight、来回切、便宜模型出错不易发现 |

### 4. 为什么这样分工
- **设计/评委 → Opus**：需要判断力——读样板、定边界、抓逻辑漏洞（评委真的抓到 2 个设计 Bug）。
- **实施 → Haiku**：规格 airtight 后是机械执行——照抄、跑迁移、列清单。
- **验证 → 回到判断力**：真实请求逐项核对，不信"它说做完了"。

### 5. 什么时候不值得用
- 需求模糊、或任务小到一次做完时，拆流水线的协调开销 > 收益。
- **"什么时候值得拆"本身就是要练的判断力**。

**对应意义（练到的 Claude Code 能力）：**
- **让 Claude Code 按"贵想便宜做"流水线执行，你只给一句话** → 驱动指令见上文"触发方式"三档。
- 背景：模型成本经济学、airtight 规格属概念知识（不用 Claude Code 也能学），降为背景。

---

### 多 Agent 沟通方式（四种通道详解）

**关键澄清：** 轮次 16 演示里 agent 之间**没有直接对话**——都经主 agent（Hub 中转）打包转发。真正的"多 agent 互相讨论"是另外的机制。

| 通道 | 机制 | 信息怎么流 | 适合场景 |
|---|---|---|---|
| **① Hub 中转** | 主 agent 把 A 的输出打包进 B 的 prompt，B 的结果回收 | 每个子代理只见主 agent 给的 prompt | 顺序流水线、每步要审查（轮次 16 用的就是它） |
| **② 文件共享** | A 写产物文件（如 spec.md），B 读文件 | 通过文件系统间接传 | 规格很长、想留痕/版本化/可追溯 |
| **③ SendMessage 队友直连** | 多个 agent 并行运行、按名字互相发消息 | agent ↔ agent 直接对话 | 真正的多方案讨论/辩论/评审 |
| **④ Workflow 数据流** | 脚本化管道，agent 返回值直接传给下阶段 | 数据流由脚本确定性编排 | 大批量、流程固定、可重复跑 |

**沟通纪律（成败关键）：**
1. **向下传递必须"自包含"**：子代理看不见你与其他 agent 的对话，prompt 要打包它需要的全部上下文（文件路径/样板/上阶段输出/期望输出格式），缺一样就瞎猜。
2. **向上回收必须"结构化"**：要求返回固定格式（文件清单/命令/偏离项），便于逐项核对。
3. **只给"那一步需要的"信息**：别全量倾倒，保持子代理上下文干净。
4. **便宜模型做完必须验证**：真实请求逐项核对，不信"它说做完了"。

**决策准则（什么时候用哪种）：**
- 简单流水线（设计→实施）→ Hub 中转够用
- 需要真"讨论"（方案竞争/评审）→ SendMessage 队友并行 或 Workflow judge 模式
- 大批量重复流程 → Workflow 脚本化
- 要留痕（规格可查）→ 文件共享

**一句话总结：** 沟通方式按**信息流向**选——顺序传递用 Hub/Workflow，并行讨论用 SendMessage，长规格留痕用文件。判断标准始终是：**每个 agent 拿到它那一步需要的、且只需要的上下文。**

## 轮次 18 · 多 Agent 变体：并行多专家设计 + 评审判定（panel 模式）

**日期：** 2026-08-14

**做了什么：**
- 记录"多个设计专家**并行**出方案 → 评审判定**选优/合成** → 实施"的配置（与轮次 16 的**串行**流水线对比）
- 明确：**同一模式家族**，差别在"设计环节是 1 个还是 N 个、以及怎么汇合"

### 串行 vs 并行对比
| | 串行流水线（轮次 16） | 并行多专家 panel（本轮） |
|---|---|---|
| 结构 | 设计(1) → 评委(1) → 实施 → 验证 | 设计A/B/C 并行 → 评审判定 → 实施 → 验证 |
| 优点 | 简单、每步可审查 | 多视角、互相制衡、更稳 |
| 缺点 | 只有一种视角 | 更贵、需要"方案汇合"逻辑 |

### 核心新增点：方案汇合
N 个设计专家各自独立产出方案，**不能直接拼**——必须有个仲裁者（评委 agent）做**选优或合成**：挑最好的，或把几个方案的优点合并成一份最终规格。这是并行 panel 与串行流水线最本质的差别。

### 驱动指令（两条可复制）
1. **Agent 并行**："让 3 个设计专家 agent 各自独立设计这个功能（互不干扰），再用 1 个评审 agent 对比 3 个方案，选最优或合成最终方案，然后交给 Haiku 按最终方案实施，最后验证"
2. **Workflow 脚本化**："写一个 workflow：3 个设计 agent 并行出方案（parallel）→ 1 个评委 agent 综合评审定稿 → Haiku 实施 → 验证，各阶段指定模型"

### 机制分工
- **多个 Agent 并行 spawn** → 让设计专家互不干扰、各自产出
- **Workflow `parallel()`** → 等所有设计完成，把 N 份结果一起交给评委（这就是"汇合点"）
- **评委/仲裁 agent（用 Opus）** → 对比 N 方案 → 选优或合成 → 输出唯一最终规格（判断力最高的一环）
- **SendMessage 队友直连** → 更进一步：让设计专家**互相辩论**（A 批 B 的方案、B 反驳），而非各自闷头设计

### 什么时候用
- **该用多专家**：方案空间大、取舍多、风险高（架构选型、缓存策略、是否引入 MQ）——多视角能暴露单方案盲区
- **单设计 + 评委就够**：模式明确的照样板任务（收藏夹就是——照着 cart 平移，多专家纯属浪费）
- **成本权衡**：N 个设计专家 = N 倍设计成本 + 评委成本 + 合成复杂度；**"用几个专家"本身就是取舍**，2 个够多数场景，3+ 只在真正高风险时才划算

**对应意义（练到的 Claude Code 能力）：**
- **让 Claude 用"并行多专家设计 + 评审判定"处理高取舍/高风险任务** → 驱动指令见上文两条
- **掌握"方案汇合"这一步** → 驱动指令："多个方案产出后，让评委对比选优或合成，产出唯一最终规格再交实施，不要直接拼多个方案"
- 背景：多视角的价值属团队协作常识（不用 Claude Code 也能学），但"在 Claude Code 里怎么编排、怎么汇合"是专属能力
